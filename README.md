# card-battle-rl

在一个人造的小型回合制卡牌游戏上，比较四种打法：**随机、贪心、手写规则、PUCT 搜索**，并测量「多加算力到底买到了什么」。

这个仓库从一个大得多的项目（一个真实卡牌对战的 AI agent，涉及逆向与游戏资产）中抽象而来：这里只保留**方法**，不含任何游戏代码、卡牌数据或美术资源。目的是让结论可复现、可验证、可公开。

---

## 1. 为什么做这个

上一段经历里最反直觉的发现是：**在真实卡牌游戏上，把领域知识写成规则的规划器，打败了 256 次模拟的 PUCT 搜索**。

这个结论一旦脱离上下文就很难被相信——「搜索怎么会输给几百行 if？」。所以需要一个小到能在一台笔记本上跑完、但保留了关键性质的环境，把同一件事重演一遍，并且把每一步的账算清楚：

- 搜索的收益随模拟次数怎么变化？
- 到多少模拟次数之后，再加算力就不涨了？
- 规则的知识和搜索的知识，在什么意义上等价？

---

## 2. 游戏

两个玩家，30 点生命，共同牌库池、各自洗牌。每回合：

1. 抽 1 张，获得 `min(回合数, 6)` 点法力
2. 用手牌做任意次出牌（总费用不超过法力），或结束回合
3. 结束回合时：己方随从对对手造成伤害，**本回合攻击加成清零**，对手执行它的整个回合

卡牌 8 种：

| 卡 | 费 | 效果 |
|---|---|---|
| Strike | 1 | 造成 1 点伤害 |
| Bolt | 2 | 造成 2 点伤害 |
| Heavy Strike | 3 | 造成 4 点伤害 |
| **Focus** | 1 | **本回合内，之后每次攻击额外 +3 伤害** |
| Mend | 2 | 回复 6 点 |
| Insight | 1 | 抽 2 张 |
| Golem | 2 | 召唤 1/3 随从，每回合造成 1 点 |
| Titan | 4 | 召唤 2/5 随从，每回合造成 2 点 |

**Focus 是整个实验的支点。** 它自己不打伤害，只有放在攻击牌**之前**才有价值：

```
Focus → Strike → Strike → Strike  =  3 × (1 + 3)  = 12 伤害
Strike → Strike → Strike → Focus  =  3 × 1         =  3 伤害
```

同一手牌，顺序不同，价值差 4 倍。这就是「逐步搜索」和「整回合规划」会产生分歧的地方。

攻击牌单独看都很弱（1 费 1 伤），单靠攻击牌打不死人。这是刻意的：如果原始伤害够高，Focus 就永远不值得打，顺序也变得无关。

## 3. 四个 agent

| agent | 机制 | 代表了什么 |
|---|---|---|
| `RandomBot` | 均匀随机合法动作 | 下限 |
| `GreedyBot` | 每次选即时伤害最高的牌 | **一步搜索然后停止** |
| `RulePlanner` | 无条件先打 Focus，再按伤害/费用比打攻击牌 | **把领域知识直接编码成规则** |
| `PUCTAgent` | 均匀先验的 PUCT，可调模拟次数 | **纯搜索，不含领域知识** |

三者共用**同一个评估函数**（`search/evaluation.py`）。这是关键的控制：它们唯一的差别是「怎么找」，不是「怎么读局面」。

`GreedyBot` 永远不会打 Focus——它的即时伤害是 0。这正是短视策略被惩罚的方式。

## 4. 实验设计：为什么这些数字可信

对局统计最容易自欺，所以做了三件事：

**配对种子 + 交换座位。** 每对局用同一个种子打两盘，A 先手一盘、后手一盘。这让牌运在两边互相抵消，而不是变成噪声。

**对称性自检。** 任何 agent 对自己必须打平。实测：

```
random vs random:       100W-100L  (50.0%)
greedy vs greedy:       100W-100L  (50.0%)
rule_planner vs itself:  50W- 50L  (50.0%)
```

三项都是精确 50.0%，说明配对逻辑没有位置偏差。

**Wilson 置信区间。** 而不是 Wald 区间——后者在 0% 和 100% 附近会给出退化区间，而这个实验里恰好会出现 0 胜的情况。

## 5. 结果

### 5.1 搜索次数扫描（核心实验）

PUCT 对 `RulePlanner`，每个点 60 局：

| 模拟次数 | 胜率 | 95% CI |
|---:|---:|---|
| 1 | 46.7% | [34.6%, 59.1%] |
| 4 | 58.3% | [45.7%, 69.9%] |
| 16 | 60.0% | [47.4%, 71.4%] |
| 64 | **66.7%** | [54.1%, 77.3%] |
| 256 | **66.7%** | [54.1%, 77.3%] |

复现：`python -m card_battle_rl.experiments.budget_scan --games 60`

三个读数：

1. **1 次模拟 ≈ 加了一点随机性的贪心**（46.7%，和规则打平）。搜索的起点并不比规则强。
2. **1 → 64（64 倍算力）只换来 20 个百分点。**
3. **64 → 256（4 倍算力）收益精确为零**：两个点都是 40W-20L。

第 3 点是这个仓库想说明的核心：**搜索的收益不是线性的，它会在某个点之后完全停止**。而在真实卡牌游戏里，那个点出现的模拟次数，远超实战可用的算力预算。

### 5.2 各 agent 的强度阶梯

来源：`python -m card_battle_rl.experiments.ladder`（写入 `results/ladder.csv`）

| 对局 | 胜率 | 95% CI | 样本 |
|---|---:|---|---:|
| `RulePlanner` vs `Random` | 80.8% | [72.9%, 86.9%] | 120 局 |
| `Greedy` vs `Random` | 68.3% | [59.6%, 76.0%] | 120 局 |
| `RulePlanner` vs `Greedy` | 65.0% | [58.2%, 71.3%] | 200 局 |
| `PUCT(64)` vs `Greedy` | 75.0% | [62.8%, 84.2%] | 60 局 |
| `PUCT(64)` vs `RulePlanner` | 57.5% | [48.6%, 66.0%] | 120 局 |

阶梯是 **随机 < 贪心 < 规则 ≈ PUCT(64)**。规则明显赢贪心（65%），验证了 Focus 的设计意图：短视策略会系统性错过顺序收益。

但**搜索并没有显著赢过规则**——57.5% 的置信区间包含 50%。这是一个诚实的负面结果，也是这个仓库最想说的一件事：在规则已经把关键顺序知识编码进去之后，64 次模拟的搜索买不到确定性优势。

⚠️ **注意一个内部不一致**：同一组对局（`PUCT(64)` vs `RulePlanner`），5.1 的扫描用 60 局测得 66.7%，这里用 120 局测得 57.5%。前 60 局恰好偏向 PUCT。这说明**单次 60 局的点估计并不可靠**，置信区间宽到足以容纳两种结论。表格照实列出，不做择优。

### 5.3 PPO 学习

用 PPO + GAE 训一个小网络（pointer head，14,275 参数），对手固定为 `GreedyBot`：

```bash
python -m card_battle_rl.rl.train --iterations 120 --episodes 24
```

| 迭代 | vs Greedy | vs RulePlanner |
|---:|---:|---:|
| 20 | 77.5% | 65.0% |
| 80 | **85.0%** | **82.5%** |
| 120 | 75.0% | 55.0% |

学习到的策略**不需要搜索**就能超过规则规划器（峰值 82.5%）。但后期明显震荡——小样本 PPO 的典型表现，没有做 early stopping 或模型选择。这个数字应当被读作「能学到」，而不是「稳定在这个水平」。

## 6. 三个 bug：为什么这个仓库里有一节专门讲失败

第一版 PUCT 对 `Greedy` 是 **0 胜 40 负**——比随机还差，而且**不报错**。查下去发现两个独立的符号/记账错误：

**① HP 优势的符号反了。**

```python
# 错：造成伤害后「优势」变小
hp = (state.opponent.hero_hp - state.me.hero_hp) / BASE_HP
# 对
hp = (state.me.hero_hp - state.opponent.hero_hp) / BASE_HP
```

用错版本时，搜索学到的是「**不要造成伤害**」，于是它每回合都直接结束回合，40 局全败。

**② 结束回合的节点看起来比出牌节点更有利。**

`end_turn` 会结算随从伤害并清零攻击加成，而 `play` 不会。直接比较两个不同阶段的局面，等于系统性偏袒「立刻结束回合」。修法是让评估函数把**未结算的随从伤害**投影到两边，统一口径。

**③ 剩余的法和「潜力」重复计分。**

`resolve_turn` 不清空法力，所以一个已经结束的回合仍然显示「手里还有 1 点法力能打」。评估函数必须显式判断 `turn_closed`，否则结束回合看起来总还有后手。

**④ 搜索递归爆炸。**

让 PUCT 当对手时，搜索里展开 `end_turn` 会推进对手的整个回合，而对手又是 PUCT 自己——`RecursionError`。修法是在搜索树里用 `resolve_turn` 在回合边界截断，只评估不推进。

这些 bug 的共同点是：**没有一条会抛异常**。它们表现为「agent 会下棋，但下得很差」。所以 `tests/test_search.py` 里有对应的回归测试——断言「打伤害不能让评估变差」「结束回合不能比出牌更好」。

```bash
pip install -e .

# 全部测试
python -m unittest discover tests

# 强度阶梯

from card_battle_rl.experiments.match import match
```

## 8. 这个实验**不能**说明什么

- **不能**外推成「搜索不如规则」。这里的分支因子只有个位数、回合内决策深度 3–5。真实卡牌游戏是 30–100 的分支因子、15 步以上的深度，那里的搜索需求高好几个数量级。
- **不能**说明 PPO 比 PUCT 强。两者训练预算不可比：PPO 花了约 3000 局的经验，PUCT 每次决策只花 64 次模拟。
- **评估函数是我手写的**，它的质量直接决定了 PUCT 的上限。这不是「PUCT 的真实水平」，而是「PUCT + 这个评估函数的水平」。这也是为什么 64 和 256 完全一样——瓶颈在评估，不在搜索。
- **对手是固定的贪心策略**，不是自对弈。训练目标因此是平稳的，但也意味着学到的策略可能过拟合这个特定对手。

## 9. 目录

```
card_battle_rl/
├── env/           状态模型与 toy 规则（core.py 与规则无关，toy.py 是具体玩法）
├── search/        PUCT、基线 agent、共享评估函数
├── rl/            特征编码、pointer 网络、PPO+GAE、训练脚本
└── experiments/   配对对局、Wilson 区间、预算扫描
tests/             30 个测试，含 4 个 bug 的回归用例
results/           实验 CSV
```

关键文件：

- `card_battle_rl/search/evaluation.py` — 所有 agent 共用的评估函数，也是「搜索能看到什么」的唯一边界
- `card_battle_rl/search/puct.py` — 约 150 行的 PUCT，均匀先验
- `card_battle_rl/rl/ppo.py` — PPO 与 GAE
- `tests/test_search.py` — bug 回归测试，建议先读这个
